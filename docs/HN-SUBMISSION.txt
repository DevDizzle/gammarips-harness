Hi HN. Since 2026-09-16 a Claude Code agent has been trading options in my own
Robinhood account, unattended, from a VM. A $1,000 account, small positions,
my money. Every trading day it writes a public file into
this repo: the agent's reasoning verbatim, every tool call, the fill, the exit
reason, and the losses when they happen. Start here:

    traces/

The 09-16 file is the first live day: NVDA, 2 contracts, the exit recorded the
evening it closes. The 09-15 file is the last dry run before real money, and
the better first read. You can watch the order book move against the agent between the screen and the
order, watch the sizing script cut it from 24 contracts to 18 on bid depth, and
watch it drop the rank-2 name because one contract cost more than the per-trade
cap allowed. That is the point of publishing the trace instead of a P&L chart.
A chart tells you nothing about whether the loop is sound.

How the loop works. Every night a pipeline starts from about 3,500 optionable
US names, keeps the ones that traded 3M+ shares that session, ranks those by
liquidity and takes the top 100. Bullish only, one out-of-the-money call each,
capped at 50. The whole pool is exposed to AI agents over MCP. The agent in this
repo pulls that pool at 10:00 ET, pulls 48 live books from the broker, and then
hands the decision to arithmetic: guard.py screens on spread and live volume,
sizes on bid depth, and validates the bracket. The model reads and explains. The
scripts decide. Bash is allowlisted to named scripts only.

I am not claiming the pool holds the best contracts. I tested that and it
failed: two pre-registered studies found the pool indistinguishable from
matched random optionable contracts. What the liquidity rule measurably fixes is
whether the agent can trade the thing at all. On a 60-day window the old
unusual-activity funnel left 40.5% of picks with no fill at 10:00 ET. The
liquid universe leaves 6.1%. Those are study numbers on a window ending
2026-08-14, not a live result.

The uncomfortable number, up front: the whole-pool composite under a fixed
exit is negative. I publish that instead of hiding it. The pool is a candidate
surface, not a set of winners, and whether anything works depends on entry,
sizing and exit. That is exactly why the harness pre-registers every pool name
as a row before any outcome is known and scores all of them after the close,
not only the one it picked. Scoring just your own picks cannot tell you whether
your screen works. The traces are receipts, not a track record, and I will not
be quoting a return in this thread.

The design decision I would most like to be argued with about: there is no pick
endpoint, deliberately. The MCP exposes primitives (the curated pool,
per-contract liquidity, realized excursion distributions, a queryable outcome
database, exit-rule simulation, methodology playbooks) and the agent reasons
over them to its own contract. Two agents with different objectives should
reach different answers. I think a pick-returning endpoint is both a worse
product and a liability, but I know that is an odd position in this category.

What is free and what is not, plainly:

Free, no signup, about ten seconds. Connect any MCP client to the anonymous
tier and you get the pool preview, the daily report, regime context, the
market calendar, and the playbooks:

    claude mcp add --transport http gammarips https://mcp.gammarips.com/mcp

Paid covers liquidity, enriched per-name detail, outcome history, and exit-rule
simulation. It is $29/mo for the first 100 subscribers, with a 30-day free
trial. The harness screen calls all four, so the daily loop will not run
anonymously. The harness is free and MIT; the data is what costs money.

Stack: Python on Cloud Run, BigQuery, Firestore, Polygon for options data.
The MCP server is Streamable HTTP. The agent is Claude Code with skills for
preflight, enter, monitor and review, one bounded session per phase.

I would rather be told where the loop is wrong than be told it is neat.
Everything here is educational and none of it is investment advice.
